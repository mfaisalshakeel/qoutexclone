- **2026-09-22**: Phase 6 — **Data tables, Client**. A reusable `DataTable` component — debounced search, chip filters (enum multi-select and date range), a column picker, sortable headers, a sticky header, page size and page-number controls, row selection with bulk actions, a row-click detail drawer, and cards on phones — all synced to the URL. Wired into the Traders (Users) page as the reference implementation, on top of the `/admin/users` endpoint the Server task already built.

  **The component owns UI state; the caller owns the HTTP call.** `DataTable` never knows an endpoint URL or a response's field names — it takes a `fetchPage(state)` function and expects `{items, total, pageCount}` back. Traders.tsx's version of that function is four lines: build the query string from the table's state, call `/admin/users`, reshape the response. Every other list this gets applied to will look the same, which is the point of building the shared piece first.

  **Filter and sort state lives in the URL, not component state** (`lib/table-query.ts`), the same way `Wallet.tsx`'s tab already does — a filtered, sorted, paged view is a link an operator can bookmark or hand to a teammate, and the browser's back button undoes one step at a time rather than losing the whole session. Page 1 and the default page size are left out of the URL on purpose, so the "no filters" state is a clean link rather than one cluttered with defaults.

  **Bulk actions call the existing single-row endpoints in parallel rather than waiting on a dedicated bulk API.** `/admin/users/:id/status` already exists; "Suspend selected" is `Promise.all` over the selected ids. A real bulk endpoint is worth building once a second admin list needs the same shape of action, not preemptively for the first one.

  **The backdrop that closes a drawer or a dropdown is a `<button>`, not a `<div>` with an onClick** — matching the pattern `BottomSheet.tsx` already established, and the only way to close it with a keyboard without hand-rolling `role`/`tabIndex`/key handling a real button gets for free.

  **Verified.** 598 server tests (unchanged — no server code touched by this task), 235 web tests (14 new, covering URL state parsing/serialization round-tripping, page-1-omitted-from-the-URL, and sort-column toggling through its three states), typecheck, build, lint all green. Manually verified every feature in a real browser — search, sort with URL sync, filters with URL sync and the empty-result state, the column picker, bulk selection and the action bar, the detail drawer, page size changes, and page navigation — at 1440px and confirmed zero horizontal overflow with working cards and drawer at 390px.

  **Decisions.** Sort cycles ascending → descending → ascending on repeated clicks of the same column, never to "unsorted" — an admin table without a sort order reads as broken rather than neutral. Retrofitting the other twelve admin lists onto `DataTable` is its own roadmap line, left for its own task now that the shared piece exists.

- **2026-09-21**: Phase 6 — **Period selector**, opening the admin back office. `/admin/overview` takes an optional `from`/`to` and returns three shapes rather than one flat object: `current` and `previous` (the same set of flow KPIs, scoped to the requested window and the immediately preceding window of equal length) and `snapshot` (queue depths and lifetime totals, unscoped — see Decisions). The dashboard gets a period picker (Today/Yesterday/7 days/30 days/This month/Custom) and every flow KPI card grows a ▲/▼/flat/new comparison badge against the previous period.

  **Only flow metrics get a comparison.** Registrations, deposit volume, withdrawal volume, net flow, house P&L and bonuses paid all happened *within* a window, so "vs. the same length window before it" is a real question. A pending-withdrawal count or a total-traders count is a state of right now, not a thing that happened during a period — there is no meaningful "previous period" for a queue depth — so those stay a single unscoped snapshot, refreshed independently of whatever period is selected (`AdminLayout`'s 30-second poll for sidebar badges keeps reading `snapshot` unconditionally).

  **The previous period is always the immediately preceding window of the same length**, computed from the request's own `from`/`to` rather than a fixed calendar unit — a custom 11-day range compares against the 11 days directly before it, not against "last month". The default period (no `from`/`to` given) is today in UTC, reusing the same calendar-day definition the responsible-trading and withdrawal daily caps already use, so "today" means the same thing everywhere in the product.

  Four new indexes (`User.createdAt`, `Deposit(status, confirmedAt)`, `Withdrawal(status, processedAt)`, `PromoRedemption.createdAt`) support the new range-filtered aggregates; `Trade(status, settledAt)` already existed and is reused for volume and house P&L.

- **2026-09-21**: Phase 5 — **Methods**. A sandbox card gateway and an e-wallet provider behind the `PaymentProvider` interface, with signed webhooks and idempotent crediting. Crypto is untouched.

  **Card and e-wallet are a different shape of thing from crypto, so they are a different code path, not the same function with an `if` in it.** `services/provider-deposits.ts` opens a checkout session through the provider (`createDepositDestination`) instead of deriving an address, and completes on a signed webhook instead of a chain watcher polling confirmations. Both paths converge on the same `completeDeposit` crypto already uses — unmodified — which is what makes the crediting idempotent and gives card/e-wallet deposits every bonus rule (status, coupon, promo, referral commission) for free rather than as a second implementation to keep in sync.

  **The signature is real.** `sandboxSecret` derives a per-provider HMAC key from `env.jwtSecret` the same way `MockCustodyProvider` derives deposit addresses — nothing to configure, nothing to leak, because there is no real counterparty. `verifySandboxWebhook` checks it with `timingSafeEqual` and never throws on a bad one, exactly as a public endpoint receiving a stranger's forged request should not. The sandbox's own "pay now" button builds the identical signed payload and delivers it through the identical verification path a real webhook takes; it does not shortcut around the check by calling `completeDeposit` directly. A new e2e test posts a genuinely signed body straight to `/api/webhooks/payments/card` — the actual public endpoint, not the authenticated "simulate" route — to prove the wiring, not just the maths.

  **The raw body had to be captured for signing to be checkable at all.** `express.json()` was already parsing every request before any route saw it; a `verify` callback on that same call now stashes the exact bytes on `req.rawBody`; re-serialising the parsed object would not reliably reproduce what a real provider signed.

  **Cards do not pay out**, because a real card network cannot receive an arbitrary payout to an arbitrary card — only refund a charge it captured. `CardProvider.payout` says so and refuses; `EwalletProvider.payout` is the one of the two that supports it. Wiring either into the live withdrawal path is the next task's job.

  **Verified.** 528 server tests (19 covering the signing — a tampered body, a wrong provider's signature, a missing header, malformed JSON, a missing externalId — 6 new integration tests for the checkout-to-credit path, a repeated webhook proving the idempotency, a rejected forged signature, and the card/e-wallet payout split), 221 web tests, build, lint. New `e2e/sandbox-payments.spec.ts` (3 tests, the third hitting the real public webhook endpoint) plus the wallet UI itself: the existing method picker, pending-deposit view and simulate button all needed only a `provider` field to branch on, not a rewrite — a checkout session amount in a box and a "simulate successful payment" button in place of the crypto QR/address panel.

- **2026-09-21**: Phase 5 — **Provider framework**. A `PaymentProvider` interface (create a deposit destination, verify a webhook, pay out), a registry, and a `PaymentMethod` table that is the operator-editable half of every method: enabled, fees, limits, countries.

  **The split is deliberate.** A provider's mechanics — address derivation, signature verification, sending money — need a deploy and live in code (`services/providers/crypto.ts` wraps the existing custody layer unchanged, so the crypto flow that already works keeps working). A method's fees, limits, whether it is offered, and to which countries are an operator's business and live in the database, edited without a deploy. `verifyWebhook` on the crypto provider always returns null — crypto deposits are proven by the chain watcher polling confirmations, never by an inbound webhook — which is what makes room for the card and e-wallet providers in the next task, whose whole deposit story *is* a webhook.

  **Wired into the real flows, not left decorative.** `createDeposit` and `createWithdrawal` now check `assertMethodAvailable` (enabled, offered in the trader's country — read from their profile) and `assertWithinLimits` (an operator's min/max) against the `PaymentMethod` row for the network in use, and `quoteWithdrawal` layers the method's fee on top of the existing network and platform fees. A method not yet seeded (a network just added in code) falls back to its static defaults rather than refusing every deposit on it.

Callers fetch the row themselves and pass it in.

  **Seeded from what already existed.** `DEFAULT_PAYMENT_METHODS` derives one row per entry in `NETWORKS`, so the four crypto methods already running keep their exact fees and limits after the migration — nothing silently changed underneath a live deposit form.

- **2026-09-20**: Phase 4 — **Responsible trading**. A daily loss limit, a daily deposit limit, a session reminder and a self-exclusion period, all enforced on the server.

  **A limit that only exists in the browser is a suggestion**, and the person it is meant to protect is exactly the person who will route around it. So every one of these is checked in the service that does the thing: `assertCanStake` before a position is worked out at all, `assertCanDeposit` before an invoice is written.

  **Tightening applies at once; loosening waits out a cooling-off period** (24 hours by default, configurable, 0 to remove it). Each field is compared on its own, so tightening the loss limit while raising the deposit limit does both — one now, one later — and a waiting change can always be cancelled, immediately. The session reminder is a nudge rather than a guard, so it applies at once either way.

  **Self-exclusion only ever extends.** A shorter period cannot shorten a longer one, and nothing cancels it. Withdrawals stay open the whole time: locking someone out of their own money is not responsible gambling. Sign-in is still allowed and recorded as `EXCLUDED` for the same reason — the door to the money stays open and the terminal is what closes.

  **A day is a UTC day**, and only live money counts: there is nothing to lose on practice, and a limit that counted it would be theatre.

  **Found while testing**: Prisma reads `undefined` as "leave this column alone", so clearing a JSON column needs `Prisma.DbNull`. The cancel-a-pending-change path silently kept the old value until a test caught it.

  **Verified.** 486 server tests (3 unit, 8 integration covering the cooling-off, the refusals, the extend-only exclusion and a withdrawal that must still go through), 221 web tests, build, lint. New `e2e/limits.spec.ts` (2 tests). The page and the interruption were looked at at 1440px and on a Pixel 7.

- **2026-09-20**: Phase 4 — **Bonuses**. A bonus choice at deposit time, a turnover requirement before a bonus can be withdrawn, and a progress bar that says where the trader stands.

  **Bonus money is real money on the real balance.** It is credited through `applyLedger` like everything else and can be traded the moment it lands. What a `Bonus` row holds back is the *right to withdraw* it: the amount stays locked until the trader has staked it a number of times over. The alternative — a second, shadow balance for bonus money — means two numbers that have to agree for ever, and they never do.

  **Every bonus carries a requirement, not just the chosen one.** The offer picked at checkout, a promo code, the status deposit bonus and a marketplace coupon each write their own row with their own multiplier, so nothing slips through as instantly withdrawable by accident.

  **Turnover is paid down oldest first, one bonus at a time.** Staking $10 with two bonuses outstanding is $10 of turnover, not $20 — the arithmetic anyone would check first, and the one a lazy implementation gets wrong. A withdrawal that would dip into locked money is refused with the exact amount still to stake.

  **The price is on the option.** Each offer at checkout shows what it adds *and* what it costs in turnover, because a bonus whose condition lives in terms somewhere else reads as a trick. A choice that stops applying when the amount changes is dropped rather than left selected and silently ignored at credit time.

  **Admin.** Offers have CRUD and an audited granted-bonus list; an operator can release a trader's hold without clawing money back, because taking credited money away silently leaves a balance nobody can explain. The screens land with the rest of Growth in Phase 6.

  **Verified.** 475 server tests (6 unit, 7 integration), 221 web tests, build, lint. New `e2e/bonuses.spec.ts` (3 tests): the choice and its turnover at checkout, the lock refusing a withdrawal, and a settled live position moving the bar. Found a latent flake in the process — a fresh account reads "Open (0)" before a position lands, so that assertion has to wait for "Open (1)" first.

- **2026-09-20**: Phase 4 — **Marketplace**. Payout boosters, risk-free cover, deposit coupons and practice top-ups, bought with loyalty points or with the live balance, held in an inventory until started.

  **Every effect that moves money goes through `applyLedger`.** A purchase with money is a negative `MARKETPLACE` entry that cannot overdraw; a risk-free refund is a `RISK_FREE_REFUND` written inside the same transaction that settled the losing position and spent the use that paid for it; a practice top-up is a `PRACTICE_TOPUP` on the demo account. Points are not money — they never reach a balance, are never withdrawable, and are spent with a conditional update that two simultaneous purchases cannot both win.

  **An item's configuration is copied onto the purchase.** An operator editing the catalogue changes what is on sale, never what someone has already paid for, and there is a test that edits an item out from under a purchase to prove it.

  **Everything that can only happen once is conditional.** Activating an item, spending a risk-free use, consuming a coupon: each is an `updateMany` guarded on the state it expects, so a burst of settlements or a double-clicked button cannot spend the same thing twice. One payout booster runs at a time. A window that closes is swept to `EXPIRED` every minute, and the effects check the clock themselves rather than trusting the sweeper.

  **Earning.** Loyalty points accrue from staked volume on the same path as XP, with their own switch: with experience off and the shop open, a position still earns points.

- **2026-09-20**: Phase 4 — **Email**. A nodemailer SMTP transport built from the settings an operator edits in the back office, nine templated HTML emails with plain-text alternatives, an outbox and a preview in admin, and the end of `EXPOSE_RESET_TOKEN`.

- **2026-09-20**: Phase 4 — **Registration and security**. Email verification, a password strength meter, TOTP two-factor with backup codes, a device list with "log out other devices", and login history.

  **Server.** `lib/totp.ts` is RFC 6238 over RFC 4226 written against node's crypto — forty lines of arithmetic, pinned to the RFCs' own vectors, rather than a dependency. `lib/password-policy.ts` holds the rule the server enforces (length, character classes, a short common-password list, and no using your own name or address); the meter in the browser is advice. `lib/device.ts` turns a user agent into a label a trader recognises and a coarse network into a fingerprint, so "new device" survives a phone changing IP every hour without becoming a tracking identifier — the hash keeps the address out of the row. `services/security.ts` owns enrolment (a *pending* secret until a code proves the app has it, so a half-finished setup cannot lock anyone out), backup codes (hashed like passwords, spent by an update that only touches a row still marked unused, so two simultaneous attempts cannot both win), the device list, and the login history. `services/mailer.ts` writes every message to an outbox table before anything tries to deliver it and keeps the transport pluggable; the SMTP one arrives with the Email task.

  **Sign-in.** A password on an account with a second factor now buys a five-minute challenge token carrying `purpose: two-factor`, not a session. Successes *and* failures are written to the history, because a run of wrong passwords from an address the account has never used is the thing worth seeing. A first sign-in from a new device sends an email, and a failure to send never costs anyone their sign-in.

  **Signing a device out had to bite immediately.** Revoking a refresh token only stops the next rotation, which would have left "log out other devices" doing nothing for up to the access token's lifetime — exactly the window that matters. Access tokens now carry the session id they were minted for, and `services/revocations.ts` keeps the recently-revoked ids in a Map that `requireAuth` checks: one lookup, no database round trip, rebuilt at boot so a restart cannot un-revoke anything. Password change and password reset feed it too.

  **Verified.** 386 server tests (the integration suite now runs, against `quotex_test`) including a new `integration/security.test.ts` for the cross-row parts: a link that cannot be replayed, an enrolment that is not live until confirmed, a backup code two concurrent attempts fight over, and a device list that refuses another account's session id. 221 web tests. New e2e `security.spec.ts` (5 tests) drives the meter, the confirmation link, enrolment with a real TOTP code, a backup code working once and then not, a second browser context appearing in the device list and being signed out, and a wrong password landing in the history. - **2026-09-20**: Phase 3 — **Performance**. `scripts/chart-perf.mjs` (`npm run perf:chart`) loads five thousand candles into the renderer, throttles the CPU, then pans and zooms while counting frames — and it measures the engine's own paint time separately from the browser's rasterisation, because in a headless browser the latter is done in software and would otherwise drown the number that matters.

  **The measurements** (Chromium, 5,000 candles, six long pans and twenty-four zoom steps):

  | profile | CPU | median paint | 95th paint | median frame | dropped (>25ms) |
  | --- | --- | --- | --- | --- | --- |
  | desktop 1280×800 | none | 1.3ms | 1.7ms | 16.7ms (60fps) | 0% |
  | desktop 1280×800 | 4× | 7.2ms | 9.5ms | 16.7ms | 10% |
  | phone (Pixel 7, DPR 3) | 4× | 6.2ms | 8.0ms | 16.8ms | 48% |
  | desktop 1280×800 | 6× | 11.0ms | 14.5ms | 16.7ms | 67% |

  The engine's work stays inside the 16.7ms budget at a 4× throttle — a mid-range phone — with 7ms to spare on a desktop viewport. The dropped frames on the phone profile are rasterisation: **the same run with 300 candles instead of 5,000 drops exactly as many frames (48%) and paints in the same 6.1ms**, which is the proof that neither figure depends on the size of the history. Four full-screen canvas layers being rasterised in software, at a quarter speed, is what those stalls are; a real phone does that on its GPU.

  **Two optimisations came out of the profiling.** Candles are now drawn in batches — two paths for the wicks and two runs of bodies, rather than a `strokeStyle` assignment per bar — and when bars are narrower than a pixel the ones sharing a column are aggregated into one (first open, last close, highest high, lowest low). That is not an approximation of the picture, it is the same picture drawn once per column, and it is why five thousand candles cost the same as three hundred. A touch pan also no longer paints a crosshair: a finger covers whatever it would show, and skipping it saves a full-screen layer on every frame of a drag.

  The harness stubs the history endpoint for the duration, so a pan into the past does not put a round trip inside a frame-time measurement, and the chart exposes itself on `window.__chart` in development only — it is compiled out of the production bundle.

- **2026-09-17**: Phase 2 — **Pending trades**. An order that becomes a position when a price level is reached or a time arrives. `engine/orders.ts` is pure and decides the condition; the side of a price level is resolved **when the order is placed**, from the price at that moment, and stored — an order placed above the market fires on the way up, one placed below fires on the way down. Re-deriving the side at execution time would give the wrong answer once the price has crossed and come back, which is exactly the bug that makes this kind of feature untrustworthy. A level sitting exactly on the market is refused as a market order rather than firing on whichever way the next tick happens to go.

  **Execution has the same idempotency guarantee as settlement**: the row is claimed with a conditional update *before* anything is placed, so two overlapping sweeps or a restart mid-flight can never open the same order twice — an integration test runs two sweeps concurrently and asserts exactly one position. A claimed order that then fails to open is recorded as `FAILED` with the reason and never retried: the trader asked for one position, not for repeated attempts at a price that has moved. Orders ride the settlement loop, reading prices from the feed, which knows nothing about orders — an order can no more move a price than a position can.

  **No money is held while an order waits**, because it is not a position yet. Whatever would refuse the trade at purchase — balance, a risk limit, a closed market — refuses it at triggering, and the reason is shown on the order. A market that has closed since the order was placed leaves it waiting rather than failing it. Orders carry a `goodUntil` (default 24h, configurable) so an unreached level is retired instead of waiting forever, and a per-trader cap on waiting orders.

  Both expiry modes work on an order: a duration is stored, and a clock boundary is re-validated when it fires because by then it may have passed. The terminal gains a Market/Pending switch with a price level seeded from the live tape (saying which way it will fire) or a start time, and the positions panel gains a proper `tablist` with a **Pending** tab that lists waiting orders apart from positions, each cancellable, with finished ones below showing why they failed. Every transition arrives over the socket, since an order changes state without the trader doing anything.

  **Found and fixed a real listing bug**: `listOrders` sorted by the status column, which is alphabetical — CANCELLED before PENDING — so a trader with a long history could have their live orders pushed past the limit entirely. Waiting orders now come first and whole, with a test that would catch it again.

  Verified against the running server: a price order placed just above the live BTC/USDT tape filled in about three seconds, and the position's entry price honoured the level. 15 unit tests for the trigger logic, 11 integration tests (including the concurrent-sweep guarantee, an IDOR check, the failure path and the cap), 2 e2e specs. 204 server + 24 web unit tests, 51 integration tests, lint, typecheck, format and build all clean.

- **2026-09-17**: Phase 2 — **Expiry modes**, the first task of Phase 2. `engine/expiry.ts` is pure and resolves both modes, so the countdown a trader watches and the validation that accepts their trade come from the same arithmetic rather than two implementations that can drift. **Duration** is a fixed length from purchase, now configurable per market: `Asset.durations` narrows the platform list (and can only ever narrow it — a market cannot offer 7 seconds because the platform does not), falling back to the platform list when it is null or holds nothing usable. **Clock time** expires on the next boundary — 12:05, 12:10, 12:15 — from a configurable set of steps, with a purchase cut-off (default 30s) before each boundary, a horizon (default 4h) beyond which nothing is offered, and a live "time to buy" countdown per boundary. One instant that is a boundary of several steps collapses to a single slot keeping the coarsest step, because that is how a trader reads it ("the 13:00 expiry").

  The server validates both and trusts nothing from the client: a clock trade sends only the boundary, and its length is derived server-side from the instant the position actually opens. It refuses an instant that is not a boundary, one inside its cut-off, one already past, one beyond the horizon, one that is not a time at all, and a mode an operator has turned off. A test asserts the contract that matters — every slot the server *offers* is one it will *accept*.

  New in both modes: **a position may not outlive its market's session.** An expiry after the close has no tick to be priced from, so it is refused with a message pointing at the OTC twin. `Trade.expiryMode` records how a position was bought so history can show it.

  The ticket gains a mode switch (shown only when the platform offers both), the market's own duration list, and the clock boundaries with a per-slot countdown that turns red in the last ten seconds and drops the slot when it closes; it re-fetches from the server as the list ages rather than extrapolating in the browser.

  **Also fixed a real session bug found by the suite**: `web/src/lib/api.ts` cleared the tokens whenever a refresh came back not-ok, so a 429 from the rate limiter or a 502 from a restarting instance signed the user out for no reason. Only a 401 or 403 — a refusal of the token itself — ends a session now; two unit tests cover the rate-limited and restarting cases.

  20 unit tests for the expiry engine, 9 integration tests across both modes and the per-market list, 2 e2e specs (one buys a clock expiry and asserts the countdown actually counts down), plus five new runtime settings. 189 server + 24 web unit tests, 40 integration tests, lint, typecheck, format and build all clean.

- **2026-09-17**: Phase 1 — **Risk limits**, which completes Phase 1. The house can now cap what it is on the hook for, the only honest way: **refuse a stake, never steer a quote.** `engine/risk.ts` is pure and, enforced structurally by a test, does not so much as mention a price, a payout, a tick, an outcome or settlement. - **2026-09-17**: Phase 1 — **Payout engine**. A market's base payout can now be moved by configurable rules, and what they resolve to is locked into the trade row the moment it opens. `engine/payout.ts` is pure and, like the price engine, **cannot read a trader, a position or the house's exposure** — a payout belongs to the market and the moment, not to who is asking or what they hold. That is enforced the same two ways: a structural test asserting the module imports nothing and mentions none of `prisma`/`trade`/`position`/`exposure`/`userId`/`balance`, and a behavioural test that smuggles `openPositions`, `exposure`, `userId` and `winRate` into the input and proves the result is identical.

  Three rule kinds, each validated against its own zod shape: **time of day** (a daily UTC window, which may run past midnight — the Asian session is written 22:00→06:00, and a wrapping window belongs to the day it started on), **volatility** (fires when a market is moving more or less than a multiple of the volatility it is configured for, measured from the closed one-minute candles the feed already holds; a market with too little history to measure does not fire the rule rather than guessing), and **scheduled** (a dated window for a news release). A rule is scoped to one market, one asset class, or every market; rules apply in priority order and add up, and one marked exclusive stops the rest. The history endpoint is paginated backwards — `{candles, nextBefore, price}` — and the chart pages as you scroll into the past (it pre-fetches when the view reaches within ten bars of the oldest one), with the quick timeframe row plus a menu covering all fourteen. The feed keeps only 60 candles per timeframe in memory now that the store owns history, and the ws snapshot reads from the store, so a restart draws real history instead of an empty chart.

  Generated history is its own problem and took the longest: a broker-priced market has no exchange archive, so `engine/history.ts` produces its past from the same engine that prices its present. Every page is walked with `elapsedMs === tickMs` over exactly one candle's worth of engine time (coarsened above 480 ticks, with the volatility scaled up to compensate) so a daily candle moves like a day; then it is pinned with a Brownian bridge to the price it joins — the newest page to the market's *live* price, each older page to the open of the oldest candle already stored — and its interior damped into a band that follows the market's own volatility and the span the page covers. Candle geometry is damped by the same factor rather than only the level, so a calmed page is a calmer walk and not a row of dojis with full-size wicks, and every open is stitched to the previous close, so a generated page has no gaps at all. Verified eight pages deep against the running server: AAPL 1m spans 2.4% over 40 hours and closes exactly on the live price, EUR/USD 0.7%, BTC/USDT 4.7%, gold 1d 25% over six years, 2,401 candles per market with no duplicates and the only discontinuity the 0.01–0.05% seam where generated history meets the live bucket. 18 unit tests for the generator, 5 for the timeframe table, 3 new feed tests and 11 integration tests across the store, deep paging and level stability, plus two e2e specs for scroll-back paging and the fourteen-timeframe menu.

  Retention bounds the table: fully populated — every market charted on every timeframe, a decade of daily candles — the 89 markets come to 6.1M rows, around 300MB, and pruning holds it there.

  Restart continuity needed two more pieces, both found by stopping a running server and comparing the tape: the store only ever heard about a candle when it *closed*, so the bucket open at shutdown was never written and the chart came back with a one-minute hole; and once written, the next process opened a fresh candle over the top of it, losing the bucket's original open and its high and low. The feed now exposes its open buckets, the store picks them up on every flush (so even a hard kill loses at most five seconds), and at boot the feed adopts whatever the last process was in the middle of printing. Verified across a real restart: the open bucket survived with its open preserved and its high and low intact, and the close simply moved on.

  Two real engine defects surfaced while measuring this, both now fixed with tests:

  - **The GARCH recursion was not normalised for elapsed time.** `lastShock` stored the printed return, but the variance it feeds is defined per `tickMs`; a tick covering more than one interval therefore fed back a proportionally larger shock, the recursion's effective coefficient passed 1, and the variance ran away. Realised volatility was 5.4× what the market's configuration claimed. `lastShock` is now normalised to one interval, and a test asserts realised volatility tracks the square-root law at 1, 1.5 and 3 intervals per tick.
  - **Drift and mean reversion were expressed per tick, so the engine's behaviour depended on its own tick size.** A trend accumulated linearly in tick count while volatility grows with its root, so the same configuration trended forty times as far at a quarter-second tick as at a ten-second one: AAPL swung 10% in an hour on a market whose volatility says 0.7%, then sat flat over days. `trendStrength` is now a multiple of the move a regime's own duration implies (divided by the root of its length, which needed the regime's full length in the persisted state — new column, migrated), and `meanReversion` is the share of the gap to the anchor closed per minute. The same defaults now produce 0.6% an hour and 1.7% a day for AAPL against a 0.7%/3.4% square-root reference, and a test asserts the same configuration produces the same market at 250ms, 1s and 10s ticks. Spot-following OTC twins keep up with their exchange market on a time basis too (4× per minute anchor tracking, with a reversion floor), instead of a rate that only made sense at one tick size. Admin help text for both parameters updated to their new meaning.

## Decisions

_Record product choices made without the owner here: what, why, where it's configurable._

- **A practice top-up resets to the configured figure rather than adding to it**, and is available at any balance unless an operator sets `trading.practiceRefillBelow`. Quotex tops practice accounts up on demand; a threshold is there for operators who would rather it were a reset button for a spent account than an infinite well.
- **A tournament that has not started is shown in the switcher but cannot be staked from.** Hiding it would leave a trader wondering whether they had joined; offering it would produce a refusal from the server. It is listed, with the reason it is not selectable.
- **Practice trade results are not notified by default** (`notifications.practiceResults`). A practice position can settle every five seconds; a centre full of them is one nobody reads. Live and tournament results always land, and the toast on screen covers practice while the trader is watching.
- **Notification sound and desktop alerts are per-device, in the browser.** Like the hotkeys: a phone and a desk are not the same room. Sound defaults on; desktop alerts stay off until the trader turns them on, and the browser permission is only ever requested from that click. The platform-wide switch stays in admin settings.
- **The notification centre is fed by events, never by the money paths.** Settlement, deposits, withdrawals, support and tournaments emit what they already emitted; the centre listens and writes afterwards, keyed on the event so a retry cannot duplicate it. A notification failing must never cost a trader a payout.
- **A support notification opens the desk widget rather than navigating.** The desk is a floating conversation, not a page, so the centre opens it in place — which is why those rows carry no destination.
- **Sentiment counts practice and live positions, never tournament chips.** A practice trader is still choosing a direction with intent; tournament chips are a game with different incentives, and blending them would misrepresent what the bar claims to show.
- **Sentiment is a display and is structurally prevented from becoming an input.** Same treatment as the price, payout and risk engines: a pure module that imports nothing and a test that fails if it ever mentions pricing at all.
- **The chart layout lives on the account, favourites and hotkeys in the browser.** A workspace is worth carrying between devices; a key map and a star list are per-device conveniences and not worth a round trip. The roadmap asked for the layout "per user", and this is the reading that actually follows the user.
- **Hotkey preferences live in the browser, not the account.** They are a per-device convenience — a trader on a laptop and a phone wants different things, and a key map is not worth a round trip or a table. The platform switch stays server-side in settings.
- **Repeating a position resolves its expiry server-side.** A client cannot send the original's expiry, because a clock boundary has passed by the time the button is clicked and a duration may have been withdrawn from the market. A duration repeat keeps its length or is refused; a clock repeat takes the soonest boundary still open.
- **A market's stake range wins over the platform's presets.** Presets and balance shares outside a market's min/max are hidden or disabled rather than shown and then refused by the server.
- **A pending order holds no money while it waits.** It is not a position, so it is funded and risk-checked at the moment it fires; a refusal then is recorded on the order with its reason rather than reserving a balance for hours. This matches how Quotex treats them and keeps the ledger free of holds that are not positions.
- **A price order's side is fixed when it is placed**, from the price at that instant, and stored. An order cannot be re-interpreted later, which is what stops it firing the wrong way after the price has crossed and returned.
- **A failed trigger is final, not retried.** The trader asked for one position at a level; retrying at a price that has since moved would be a different trade than the one they asked for.
- **A market may narrow the platform's expiry list, never widen it.** `Asset.durations` is filtered against the platform list, so an operator cannot create a per-market expiry the settings do not offer, and a list with nothing usable falls back rather than leaving a market untradeable.
- **A position may not expire after its market closes**, in either mode. There would be no tick to price it from; the refusal points at the OTC twin, which never closes.
- **A clock trade sends only the boundary.** The position's length is derived server-side from the instant it opens, so a client cannot claim a duration that does not match its expiry.
- **Risk limits count live money only.** Practice and tournament stakes are not the house's exposure, so they never enter the book and never block a practice trader. A trader's own per-market cap still applies inside whichever account they trade.
- **Risk is checked inside the position's transaction**, not with a market-wide lock. Two simultaneous trades can overshoot a house limit by at most one stake; serialising every trade on a market to close that window would cost far more than it saves.
- **No payout rules are seeded.** A fresh install pays every market its base payout, which is the neutral, predictable default; the admin Payouts screen explains itself with an empty state and a preview, so an operator can build the first rule and see its effect before saving it.
- **Payout rules are blind to traders by design.** They read the clock, the calendar and how much a market is moving — never a position, an exposure or a user's history. Same hard rule as the price engine, enforced by the same structural and behavioural tests. Risk controls (next task) limit *new stakes*; nothing steers a quote or a payout toward an individual.
- **Volatility thresholds are ratios, not absolute moves.** "Moving more than 1.5× its normal" works for a rule scoped to every market, where an absolute per-minute figure would only suit one. A market without enough history to measure does not fire the rule.
- **E2E browser binary**: `playwright.config.ts` honours `E2E_CHROMIUM_PATH` so sandboxes with a pre-installed Chromium don't download another. CI installs the pinned browser and ignores the variable.
- **Prettier scope**: code only. `*.md` is ignored so the owner's docs keep their own formatting.
- **Settings vs env**: env stays the bootstrap (DSN, secrets, ports, feed provider) and seeds the *defaults* of runtime keys; anything an operator would change while running lives in the settings registry. Existing deployments keep their current behaviour until someone edits a value in admin.
- **Live data is opt-in**: `FEED_PROVIDER=simulated` (the default) keeps every market broker-priced. The gate lives in the feed, not the registry, so the registry stays pure provider plumbing and is testable without env stubbing.
- **Forex/stock quotes**: implemented against a Twelve Data-shaped `/price` endpoint because it has a usable free tier, but `MARKET_DATA_URL` accepts any service with the same response shape. Real credentials are the owner's to supply.
- **One engine for every simulated market**: rather than keep the old random walk for exchange-traded markets and add a second engine for OTC, all simulated pricing runs through the OTC engine. Non-OTC markets keep their session gating and will be driven by a real provider in the "Real feeds" task; OTC markets are broker-priced by definition.
- **RNG state column**: mulberry32's state is a uint32, which does not fit MySQL's signed `INT`. The column is `INT UNSIGNED` (found by running it — the first flush failed with "out of range").
- **Session ownership**: calendars are shared records (forex, metals/energy, US equities, US/European index CFDs) rather than per-asset hours, so one edit moves every market on that venue. Crypto and OTC deliberately carry no calendar.
- **Closed markets freeze**: rather than keep generating candles nobody can trade, the feed skips markets outside their session. The last tick stands until the market reopens.
- **Crypto quote currency**: the original markets were BTC/USD; the catalogue quotes crypto in USDT because that is what the exchange feed prices. A data migration renamed the assets and their denormalised trade symbols rather than leaving two conventions in the table.
- **OTC pricing premium**: OTC twins get +3% payout (capped at 95%) and 1.15× volatility, mirroring how brokers price their own books. Both numbers live in `data/markets.ts` and become per-asset admin settings in the OTC engine task.
- **Outbox before transport**: every email is written to `EmailMessage` and then delivered, so a deployment with no SMTP configured still has a record an operator can read rather than a silently dropped verification link.
- **Secrets in the settings registry**: a key marked `secret` can be written from the back office but never read back out of it, and never appears in the public settings. The SMTP password is the first; env still seeds its default, so a deployment can keep it out of the database entirely.
- **Self-exclusion never blocks a withdrawal, or the sign-in that reaches one**: trading and deposits close, the account does not. Anything else holds someone's money hostage at the worst possible moment.
- **A shared crediting path, not a shared deposit function**: crypto's address+chain-watcher and card/e-wallet's checkout+webhook are different enough mechanisms that forcing one function to branch on which would have made both harder to read. They converge only at `completeDeposit`, which is the one place idempotent crediting and every bonus rule need to live.
- **Cards are deposit-only**: a real card network has no way to push money to an arbitrary card on request, only to refund a charge it captured. `CardProvider.payout` refuses rather than pretending; e-wallet and crypto are the withdrawal-capable methods.
- **Provider mechanics in code, method configuration in the database**: a `PaymentProvider` implementation needs a deploy; the fees, limits, countries and on/off switch for one of its methods do not, and are edited from the back office instead.
- **Crypto has no webhook**: it is proven by the chain watcher, so `CryptoProvider.verifyWebhook` always returns null. Card and e-wallet, arriving next, are webhook-driven from the start.
- **Number format, not currency conversion**: the profile changes how amounts are written, never what they are worth. Showing a balance converted into another currency means the balance itself has to be denominated in it — a real change to the ledger and a business decision, not a display preference.
- **Avatars are presets until there is an object store**: Phase 8 brings the upload interface for KYC documents; avatars will use the same one.
- **Loosening a limit waits, tightening does not**: the moment someone wants their limit raised is the moment it is working. The session reminder is exempt — it is a nudge, not a guard.
- **Bonus money lives on the one balance**: a bonus is credited normally and a `Bonus` row records the turnover that has to be met before it can leave. Two balances that must reconcile is the alternative, and it always drifts.
- **Every bonus carries turnover, whatever its source**: promo codes, status bonuses and marketplace coupons all write a bonus row. A withdrawable-by-default bonus would be the exception nobody documented.
- **Turnover is not multiplied across bonuses**: one stake pays down one bonus, oldest first.
- **Forfeiting releases the hold and never claws back the money**: an operator settling a complaint wants the trader able to withdraw, not a balance that silently shrank.
- **Points are a separate currency from XP**: spending experience would demote a trader, so the marketplace has its own balance earned on the same activity. Neither is money.
- **Marketplace items are disabled, never deleted**: an inventory row references the item it came from for ever, and a support question about a purchase from last year has to be answerable.
- **XP never becomes money**: experience and badges are a record of activity. They do not go through `applyLedger`, they cannot be spent, and nothing in the settlement path reads them. When the marketplace arrives it will decide for itself what, if anything, converts.
- **Practice earns no XP by default**: the practice balance refills on demand, so experience earned from it would be unlimited and the ladder meaningless. `growth.xpFromPractice` exists for operators who disagree.
- **Achievements evaluate on a debounce, not on every settle**: measuring a trader's whole history costs several aggregates and a binary-options trader settles constantly. Thirty seconds per trader, plus a catch-up whenever the page is read.
- **Status perks never touch the quote**: the payout bonus is applied to the trader's own position from their lifetime deposits alone. The market's payout is unchanged, and nothing on that path reads a position, an exposure or a result. Tournament trades are exempt so a contest stays a contest, and practice trades are not, so the practice account rehearses what live money would actually pay.
- **A deposit is paid at the level held before it**: the bonus for the deposit that promotes someone is calculated from their total *before* the credit. The alternative reads as a retroactive promotion and makes the threshold ambiguous.
- **Two listeners, not one**: the notification centre and the mailer subscribe to the same events separately. Sharing the wording would make both worse — a notification is read in the app, an email is read away from it.
- **Email verification is a three-way setting** (`off` / `optional` / `required`), matching how brokers differ: optional asks and nags, required blocks deposits and withdrawals but never trading, because the gate is about money moving, not about using the platform.
- **Device identity is deliberately coarse**: a browser label plus the /24 (or IPv6 /64-ish prefix), hashed. Finer would call a phone a new device every hour; finer still would be fingerprinting, which is not what a device list is for.
- **Revoked sessions live in memory, not the database path**: checking `RefreshToken.revokedAt` on every authenticated request would be a query per request. The Map only ever holds ids whose access tokens could still be alive, and is reloaded at boot.
- **Practice starting balance** moved to `trading.practiceStartBalance` (default $10,000) and the refill threshold to `trading.practiceRefillBelow` (0 = always allowed), matching Quotex's refillable demo account.
